## Project

Streamlit application for translation using Cohere Labs Tiny Aya Global on Apple Silicon with MLX. The app translates text and documents across 67 languages with local inference via the `mlx-community/tiny-aya-global-8bit-mlx` model.

## Stack

- Python 3.13+ with uv for project management
- Streamlit for UI
- watchdog for Streamlit's file watcher, listed in `dependencies` **explicitly** because Streamlit's own requirement on it is gated `sys_platform != 'darwin'`. On macOS Streamlit therefore ships *without* it and falls back to `PollingPathWatcher`, which is what prints "For better performance, install the Watchdog module" on every launch. Streamlit's accompanying `xcode-select --install` hint is stale — the macOS wheel (`cp313-cp313-macosx_11_0_arm64`) is a compiled FSEvents binding but is **prebuilt** on PyPI, so nothing is built locally. It belongs in `dependencies` rather than the `dev` group because the server process imports it, not the tests. Confirm it took with `uv run python -c "from streamlit.watcher import path_watcher; print(path_watcher.get_default_path_watcher_class().__name__)"` → `EventBasedPathWatcher`
- mlx-lm for translation inference on Apple Silicon
- liteparse for parsing uploaded documents (required dependency: one ~11 MB wheel with no transitive deps)

## Structure

- `streamlit_app.py` — main app: config, pure functions, Streamlit UI
- `test_streamlit_app.py` — pytest unit tests for pure functions
- `test_streamlit_ui.py` — pytest UI tests for Streamlit interface
- `.streamlit/config.toml` — Streamlit's default theme, light and dark modes
- `.github/workflows/` — `ci.yml` (checks + auto-publish release) and `release.yml` (manual bump), sharing `.github/scripts/release-notes.sh`; see Automation and Releases
- `.claude/settings.json` — ruff/ty/pytest hooks and the protected-path guard; see Automation
- `assets/screenshot.png` — README hero image; see Screenshots

## Commands

```bash
uv sync                                                      # install dependencies
uv run streamlit run streamlit_app.py                        # run the app
uv run pytest test_streamlit_app.py test_streamlit_ui.py -v  # run tests
uv run ruff check --fix .                                    # lint
uv run ruff format .                                         # format
uv run ty check                                              # type check
```

When working with Python, invoke the relevant `/astral:<skill>` for uv, ty, and ruff to ensure best practices are followed.

- Bare `python` is **not** on `PATH` (`command not found: python`); everything goes through `uv run`, one-off scripts included (`uv run python <script>`)
- `uv run streamlit docs st.<command>` prints the exact signature and docstring from the *installed* Streamlit — use it instead of recalling an API from memory. The `developing-with-streamlit` skill routes to version-matched reference docs bundled inside the venv at `.venv/lib/python3.13/site-packages/streamlit/.agents/skills/`, not to anything in this repo; that tree also carries ready-made theme configs under `assets/templates/themes/configs/` (12 presets, `nord.toml` among them)
- A throwaway `uv run python -c` that **imports** `test_streamlit_app` or `streamlit_app` buries its output under dozens of `missing ScriptRunContext!` warnings, because importing the app runs Streamlit calls outside a script run. For a quick calculation, inline the few lines you need rather than importing the module

## Automation

- CI (`.github/workflows/ci.yml`) has **two jobs**. `check` runs on `macos-latest` (Apple Silicon, so `mlx-lm` installs natively) for pushes to `main` and PRs: `uv sync --locked`, `ruff format --check .`, `ruff check .`, `ty check`, then `pytest test_streamlit_app.py test_streamlit_ui.py -q`. Note `--check` — unformatted code fails CI rather than being auto-fixed. `release` is the auto-publish job described under Releases
- The sync is `uv sync --locked`, not a bare `uv sync`. `uv.lock` records the project's own version, so a hand bump that edits `pyproject.toml` alone leaves the lock stale — and a bare `uv sync` **rewrites it in place and goes green**, which would let the `release` job tag a commit whose lock disagrees with its pyproject. `--locked` fails the run instead. The same swap was made in `release.yml`, which claims "same gate as ci.yml" and now actually is
- `concurrency` is declared **per job**, not at workflow level. A workflow-level `cancel-in-progress: true` cancels the *whole run*, so a second push landing during a release could kill the job between `git push --tags` and `gh release create`, leaving a pushed tag with no release. `check` keeps `ci-${{ github.ref }}` / cancel-in-progress; `release` takes `group: release` / **no** cancel, the same group `release.yml` uses, so the two release paths serialize against each other repo-wide
- `.claude/settings.json` hooks: `PostToolUse` runs `ruff check --fix . && ruff format .` after every Edit/Write (edited files may be reformatted underneath you), `Stop` runs `ty check` + `pytest` at session end, and a fail-closed `PreToolUse` hook blocks edits to `uv.lock` and `.streamlit/secrets.toml`

## Releases

- Versioned with SemVer in `pyproject.toml` (`version`); currently pre-1.0 (0.x). First tagged release was `v0.8.2`. Tags carry a `v` prefix; `pyproject` stays bare
- There are **two** ways to cut a release, and both **publish immediately**. There is no draft and no review step: the release goes live, watchers are notified, and the README's release badge moves the moment the job finishes. Deleting a release afterwards does not unsend the notification, so the review that used to happen on the draft has to happen *before* the push — in the commit subjects, which are now the notes:
  - **`Release` workflow** (`.github/workflows/release.yml`), run from the Actions tab with a `patch`/`minor`/`major` choice. It runs the full CI gate, bumps the version, generates notes, commits, tags, pushes, and publishes. This is the path that *performs* the bump, and `uv version --bump` is the reason to prefer it
  - **CI's `release` job** (`.github/workflows/ci.yml`), which publishes a release for any version bump that lands on `main` by hand. Bump `pyproject.toml` + `uv.lock`, commit, push — the tag and the published release follow automatically
- Both publish steps pass **`--verify-tag`**, which is not redundant with the tag push in the step above it. `gh release create` *creates* a missing tag itself, resolving it against the default branch's HEAD — so a tag push that failed silently would produce a live release attached to the wrong commit. With the flag the step aborts instead, leaving the tag and release consistent. `--latest` is deliberately unset, which is **not** the same as passing it: unset means GitHub picks the Latest release automatically from date and version, which is right while the newest release is always the highest version. Each step captures `gh`'s stdout (the release URL) into `$GITHUB_STEP_SUMMARY`, because with nothing to review in the Releases tab the run summary is where the link is wanted
- The two cannot double-release, for **two independent reasons**, and the first is the same GITHUB_TOKEN rule that shapes `release.yml`: the bump commit it pushes is authenticated with `GITHUB_TOKEN`, so it does not start a CI run *at all*. Even if it did, CI's gate skips any version that is already tagged — which `release.yml` has done by then. They also share the `release` concurrency group, so they cannot interleave
- CI's gate is **"pyproject declares a version with no tag"**, deliberately not a diff against the parent commit. A push can carry many commits, a re-run would fire twice, and a force-push has no useful parent; the tag check is idempotent and answers the same question. It reads the remote (`git ls-remote --exit-code --tags origin`), which is the real source of truth for "has this shipped"
- CI's `release` job runs on **`ubuntu-latest`**, not the `macos-latest` the checks need — it is plain `git` + `gh`, and macOS runners bill at 10x. It reads the version with the runner's preinstalled `python3` + stdlib `tomllib` rather than `uv version`, the project's usual route: `uv` performs interpreter discovery and would download a whole Python to read one TOML field, on **every** push to `main` including the ones with nothing to release
- Its `permissions: contents: write` is declared **at the job**, overriding the workflow-level `contents: read`. The `check` job stays read-only
- There is no artifact to publish: `pyproject.toml` has no `[build-system]` and `uv.lock` records the project as `source = { virtual = "." }`. A "release" here is only a tag plus a GitHub Release
- The workflow bumps with `uv version --bump <part>`, which rewrites `pyproject.toml` **and** re-locks `uv.lock` in one command — a version bump touches **two** files, because the lock records the project's own version. Bumping by hand and forgetting the lock leaves it to be rewritten by the next `uv` command, potentially after tagging
- Release notes are generated from **conventional commits** since the previous tag, grouped into Features / Fixes / Performance / Refactoring / Documentation (`chore`/`test`/`ci`/`build` are omitted as noise; the compare link covers them). GitHub's own `--generate-notes` is useless here — it aggregates merged PRs, and commits land directly on `main`. That output now ships **unreviewed**, so a commit subject is user-facing copy the moment it is pushed. The hand-written Highlights/Requirements/Run blurb that the draft existed for is gone; if it is ever wanted back it belongs in `release-notes.sh` as a static footer shared by both paths, **not** as a restored draft on one of them
- That generator lives in **`.github/scripts/release-notes.sh`**, called by both workflows so they cannot drift into describing the same commits differently. It takes the output path as `$1` and `VERSION`/`REPO_URL` from the environment, and must run **before** the new tag exists or `git describe --tags --abbrev=0` returns the tag being created and the range collapses to nothing. It runs on **both** runner OSes, and macOS ships **bash 3.2**, so no bash-4 syntax: no arrays, no `${x,,}`. That is why the empty-range (first-release) case is spelled as two separate `git log` calls instead of an interpolated `$range` — the empty form needs an unquoted expansion, and bash 3.2 has no safe empty array. `set -o pipefail` is on, so each `section` needs its `|| true`: `grep` exits 1 for a commit type absent from the range, which would otherwise fail the run
- The workflow is `workflow_dispatch`, **not** tag-triggered, and that is deliberate: a tag pushed with `GITHUB_TOKEN` does not trigger other workflows, so an `on: push: tags:` release job would silently never fire
- Every `${{ }}` value is passed through a step-level `env:` block rather than inlined into a `run:` script — the standard defense against workflow command injection. `github.ref_name` is a branch name and must never be inlined
- `main` has no branch protection or rulesets, which is what lets the workflow push the bump commit directly. Adding protection means allowlisting the Actions actor
- Hand-bumping is now a **supported path rather than a fallback**: `uv version --bump <part>` → commit `pyproject.toml` + `uv.lock` **together** → push to `main`, and CI tags and publishes the rest. Do not tag by hand as well; the gate would then see the tag and skip, leaving no release. If CI is bypassed entirely, the fully manual sequence is still bump → commit both files → `git tag -a vX.Y.Z` → `git push origin vX.Y.Z`, and tags must be pushed explicitly — a branch push (including via GitHub Desktop) does not carry them, verify with `git ls-remote --tags origin`
- Committing the two files **separately** is the one way to get a wrong result: pushing a `pyproject.toml` bump without its `uv.lock` fails `uv sync --locked` in `check`, and `release` never runs (`needs: check`) — which is the intended outcome, but the release simply does not appear rather than announcing why. The failing step names it

## Screenshots

`assets/screenshot.png` is the README hero image: the Text tab in dark mode, English → French, `hello world` → `Bonjour le monde`. Regenerated 2026-08-08 at 978×833 and current as of the design pass — it shows the subtitle caption, both tab icons, the centred swap, the settled output as full-contrast monospace `st.code`, and icons on Translate/Download. Regenerate it whenever the theme or that tab's layout changes. It is **binary, so nothing in CI can catch it going stale** — it silently advertised the removed Nord theme until pixels were sampled and colour-managed. Every trap below produces a plausible-looking but wrong image, which is why they are worth writing down.

- Serve it on a **free port**: `uv run streamlit run streamlit_app.py --server.port 8502 --server.headless true`. 8501 on this machine is usually another project's app, and Streamlit will happily start on a different port without saying so loudly
- The shot needs a **real translation**, not an empty app — but the old reason for saying so is gone. It used to be that the output `text_area` was `disabled=True`, so genuine output rendered in the same muted grey as placeholder text; settled output now goes through `render_output`/`st.code` and reads at full contrast, and the empty-state placeholder is `Translation appears here`. Weights are already in `~/.cache/huggingface` (~3.6 GB — `du -sh` prints `3.3G` because it reports GiB; the rest of the repo quotes 3.6 GB and that is the same number), so the Translate click costs seconds rather than a download
- **Move the pointer off the button before capturing.** Clicking Translate leaves the cursor hovering it, and Streamlit's primary hover is `rgb(255,0,0)` against the resting `rgb(255,75,75)`; a baked-in hover state reads as a deliberate colour choice, not a mistake. Verify with `getComputedStyle(btn).backgroundColor`, not by eye
- Hide the Streamlit toolbar (`[data-testid="stToolbar"]`, plus `stDecoration`/`stStatusWidget`) by setting `display:none` from the page, and **re-hide after every rerun** — a translation rebuilds the DOM and brings it back
- macOS `screencapture` **does not work from this environment** — `could not create image from rect` for every region *and* every `-D` display, because the process has no Screen Recording permission and only the user can grant it. Do not burn time debugging the rect; use the Chrome extension
- The Chrome `computer` **`screenshot`** action downsamples (a 1080px-wide viewport returns 883px), while the **`zoom`** action re-renders its region at *native* resolution. `zoom`'s `region` is expressed in the **downsampled screenshot's** coordinate space, not viewport space — scale viewport coords by the downsample factor first. Out-of-range values fail with a message that misleadingly quotes the viewport size, which sends you looking in the wrong place
- Chrome embeds a `Google/Skia/…` display profile, so **captured pixels are not sRGB** — the page background reads `#101216` against the configured `#0e1117`. Convert with `PIL.ImageCms.profileToProfile(img, src, ImageCms.createProfile("sRGB"))` before saving. Neutrals then land byte-exact; a saturated primary clips ~4% (`#ff4b4b` → `#f54b4c`) **identically under all four rendering intents**, so that residue is the floor of the round trip and not an intent left to tune
- Sample the *fill*, not the centre, when spot-checking a button — dead centre is the label glyph, and white-on-red anti-aliasing returns a pink that looks like a colour bug
- Pin the theme before capturing: `localStorage.setItem('stActiveTheme-/-v2', '"Dark"')` then reload. The key is versioned (`-v2`), and leaving it at `"System"` means an OS appearance change mid-session silently reshoots in light
- Buttons now carry icons, so `button.innerText` is `"translate|Translate"` — selecting a button by its label text fails. Use the key-derived class Streamlit emits, `.st-key-translate button`
- The last regeneration confirmed two things worth keeping: the neutrals land **byte-exact** after the sRGB conversion (`#0e1117` page, `#262730` both panels) and the primary clips to `#f54b4c`, the documented ~4% floor. Both panels reading `#262730` is also a live check on the `codeBackgroundColor` pin — the input `text_area` and the output `st.code` are the same shade side by side, which is the whole point of it

## Conventions

- Pure functions are defined above `import streamlit` with deferred imports for `mlx_lm` and `liteparse` inside their bodies, so tests can patch them without loading the model stack
- Config is hardcoded as module-level constants (`MODEL_ID`, `DEFAULT_TEMPERATURE`, `DEFAULT_MAX_TOKENS`, `MAX_INPUT_TOKENS`, `MAX_CHUNK_TOKENS`, `DOCUMENT_TYPES`, `MAX_UPLOAD_MB`) at the top of `streamlit_app.py`, plus shared UI constants (`PANEL_HEIGHT`, `SAME_LANGUAGE_WARNING`, `NO_OUTPUT_WARNING`) reused across both tabs; source-level tests guard against re-inlining `height=450` or duplicating either warning literal
- `streamlit_app.py` sets `TRANSFORMERS_VERBOSITY=error` via `os.environ.setdefault` at the top of the file, muting transformers' image-processor alias warnings that Streamlit's module watcher otherwise triggers on every rerun
- Language selectboxes use the flat `LANGUAGES` list (67 items) with collapsed labels and Streamlit's built-in type-to-search. Both tabs now carry the **same `[10, 1, 10]` from/swap/to row** inside `st.container(border=True)`. The Document card holds a **second** row — the uploader and its OCR notice — because describing a document source is one operation; leaving them as separate full-width siblings drew the tab's only stroke around its least consequential third (two dropdowns) while the control that must be acted on first had no grouping at all
- The Text tab's selectboxes carry `on_change=clear_translate_output`, which drops a settled translation when either picker moves. The settled output is an unlabelled `st.code` block, so changing To from French to German left the card asserting English → German above a panel still holding French, with Download still offering it. The Document tab deliberately answers this the *other* way — it keeps the output and discloses the real pair in `doc_meta` — because it has a provenance surface to disclose into and the Text tab does not
- The Text tab's download name is captured into `st.session_state.download_name` at the moment the output settles, not built at the button: `target_lang` keeps moving afterwards, so a name read at render time describes the dropdown rather than the bytes. Same reasoning as `record_document_provenance`. `AppTest` cannot verify it — `DownloadButton`'s proto has no `file_name` field, only a media-manager `url` — so the wiring is guarded at source level by `test_text_download_button_uses_the_recorded_name`
- Swap button (`:material/swap_horiz:`, `type="tertiary"`, `help=` tooltip) flips languages via `st.session_state` and moves output into input. **Both tabs have one now** — `swap_doc` calls `swap_doc_languages`, which flips languages *only*: a document's source is an uploaded file, so there is nothing to move the output into, and `doc_output` is left alone because the upload has not changed and `clear_doc_output` owns that invalidation. The tooltip says "Swap languages and move the translation into the input" on the Text tab, because the plain "Swap languages" hid two destructive side effects (output wiped, input overwritten, not undoable)
- The swap buttons pass an **empty label**, which `best-practices.md` forbids in general — but `st.button` is the exemption: it has no `label_visibility`, its docstring omits the "never set an empty label" paragraph that 14 other widget docstrings carry, and `button.py` is not among the modules calling `maybe_raise_label_warnings`. Icon-only is Streamlit's own idiom here and there is no in-API alternative. The residual cost is real and unfixed: `DynamicIcon` renders the Material glyph as a `translate="no"` span with **no `aria-hidden`**, and `help=` becomes `aria-describedby` only while the tooltip is open, so the computed accessible name is the ligature text — a screen reader announces "swap_horiz, button"
- `warning_slot = st.container()` is declared above the panels so the translation block (which runs later in the script) can place warnings above the input/output without needing `st.rerun()`
- Side-by-side input/output panels. The input is a `st.text_area` capped at `MAX_INPUT_CHARS` (30,000); that cap reaches the browser as HTML `maxlength`, so an over-long paste is clipped with **no event the server can see**. The placeholder names the number, and **which limit binds depends on the script**. Measured with the model's own tokenizer: 30,000 characters of English prose is ~5,756 tokens, comfortably inside `MAX_INPUT_TOKENS`, so for Latin scripts the character cap is what a user actually hits — silently. The same 30,000 characters of Thai is ~24,897 tokens, so there the token gate fires first and announces itself with its own count. The placeholder covers the failure that has no other surface; the token gate covers itself
- Output is rendered into an `st.empty()` placeholder (`output_placeholder`) so streaming can replace it progressively. The **settled** state goes through `render_output` too, exactly like the Document tab; the disabled `text_area` survives only as the *empty* state, where it supplies the placeholder (`Translation appears here` — an instructional phrase, because a bare noun in the same muted grey was indistinguishable from a one-word translation) and balances the input panel. It used to render the settled value, and Streamlit paints disabled content at `fadedText40`: measured **2.17:1 light and 3.53:1 dark**, i.e. the finished translation was *less legible than its own placeholder*, and a disabled textarea is unselectable, so it could not be copied at all — only downloaded
- Streaming fills the placeholder via the `render_output(placeholder, text)` helper — `st.code(..., language=None, wrap_lines=True, height=PANEL_HEIGHT)`, not `text_area` — repeating a widget call in the same script run would collide on the auto-generated element id, but `st.code` is non-widget and replaces freely; both tabs render output through this one helper
- Translate button (`type="primary"`, `width="stretch"`) uses a callback + flag pattern (`_do_translate`); after streaming, the translate block calls `st.rerun()` so the disabled output `text_area` and download button re-render with the final value
- Translate block validates input (`tokenize_prompt` + `MAX_INPUT_TOKENS` check) and wraps streaming in `try/except` (errors → `warning_slot.error`, empty output → `warning_slot.warning`)
- Download button (`type="secondary"`, `width="stretch"`) uses `st.download_button` to save the translation as `translation.txt`. The Document tab's equivalent is named from the upload instead — `document_download_name` gives `report.pdf` + French → `report-French.md`, because every output being `translation.md` left `translation (1).md`, `translation (2).md` with nothing to tell them apart. It splits on the *last* dot and leaves a dotless or dot-leading name intact
- Controls row is `st.columns(2)`, mirroring the side-by-side input/output panels — **not** `st.container(horizontal=True)`, even though Streamlit's own best-practices doc prefers horizontal containers for button rows. The container's children are `flex: 1 1 fit-content`, so a stretched button grows from its *intrinsic* width and the row ends up content-proportional rather than 50/50: measured in-browser, Translate 460.6px against Download's 465.4px, versus the panels' 461/461 directly above, and a 14px gap against their 16px. Columns are a proportional grid, which is what mirroring the panels needs. **Those figures are historical** — they were measured under the old theme's `baseFontSize = 14`, and the theme now inherits Streamlit's 16px base, which shifts every intrinsic width and gap. The conclusion survives (a flex row is content-proportional, a column grid is not); the specific pixels do not, so remeasure before citing them
- Full-width buttons use `width="stretch"` — Streamlit 1.58's replacement for the deprecated `use_container_width`; a source-level test in `test_streamlit_app.py` guards against reintroducing the old arg. There are **four** of them (translate, download, translate_doc, download_doc), not six
- The two swap buttons are pinned to `width=40` inside `col.container(horizontal=True, horizontal_alignment="center")` and are **deliberately not stretched**. Every `st.columns` child picks up `min-width: calc(100% - 1.5rem)` below the 640px breakpoint *regardless of its weight*, so the 1-unit swap column becomes a full row — and a `type="tertiary"` button paints no background or border, so a stretched one became an **invisible full-row tap target** between the two pickers: measured 425×40 at a 500px viewport, clickable edge to edge, one stray tap from wiping the Text tab's output. A fixed 40 clamps to the parent, so the desktop rendering is unchanged and only the hit area moves. It does **not** rescue the 640–800px band, where the column shrinks toward the 16px icon and 40 clamps with it
- The four action buttons carry icons (`:material/translate:` on both produce actions, `:material/download:` on both save actions) — previously they were distinguished only by fill colour, which reads as two peers when Translate is the expensive state-changing operation and Download is a passive export that is disabled most of the time
- The Text tab reserves its output panel with `output_placeholder.skeleton(height=PANEL_HEIGHT)` at click time, rather than announcing the translation with a bare `st.spinner` at the script cursor — that cursor sits below both the panels and the controls row, the off-the-fold trap `ensure_model` and `doc_status_slot` already document. `warning_slot` was rejected because it sits *above* the panels and would shove the row down for the duration. The skeleton reflows nothing and clears the previous translation, which used to sit there looking current. There is **no `st.spinner` alongside it** — that would be a second indicator for one operation, at the very position the reasoning rules out
- **Every exit path of the Text translate block ends in `st.rerun()`**, so the panel is always repainted from `translate_output` rather than patched in place. That is what lets the *empty state* come back as its `text_area`, which cannot be re-emitted in the same run (the widget id would collide) — an earlier version painted a blank `st.code` instead and left a featureless grey rectangle after a first-run failure
- `translate_notice` (`("warning" | "error", text)`, or `""`) carries the message across that rerun, drained and cleared immediately under `warning_slot`. Without it the rerun that repaints the output would also discard the explanation for it. The three *pre-stream* checks — empty input, same language, over token budget — do **not** rerun and still write to `warning_slot` directly
- On empty output the block clears `translate_output` and `download_name`, because **state has to agree with the message**. An earlier version restored the previous translation to clear the skeleton, which put a downloadable translation of *different input* directly beneath "the model returned an empty translation" — verified by reproduction, download button live, name still `translation-French.txt`
- A mid-stream failure now **keeps the partial**, with a `translation-<Target>.txt` name and a "failed after partial output" error, matching what the Document tab already did. Before, the streamed text was visible but unreachable and vanished on the next rerun
- Source-level tests read `streamlit_app.py` as raw text and count occurrences across the **whole file, comments included** — a comment that mentioned `width="stretch"` in prose broke `test_buttons_use_width_stretch` with `assert 6 == 5`. Before writing a literal into a comment, check whether a test counts it — currently `width="stretch"` (4), `width=40,` (2), `height=450`, `.code(`, `"translation.txt"` (1), `"translation.md"` (1), and the two warning strings. Naming an API in prose is otherwise fine, and is often the whole point of the comment
- A **second genre** of source-level test matches against `"".join(_APP_SOURCE.split())` — whitespace-stripped, so re-wrapping a call is safe, but the exact syntax is pinned. Two exist: `cached_document_chunks(uploaded.getvalue(), st.session_state.doc_source_lang)` and the `elif (loaded := ensure_model(doc_status_slot)) is not None:` guard. Renaming either variable or reordering those args fails a test that no literal count would flag, and both guard wiring `AppTest` cannot reach
- Translation model loads **lazily**: `@st.cache_resource def load_model()` wraps `mlx_lm.load`, and `ensure_model(warning_container)` calls it from inside the translate handlers — after the free empty-input and same-language checks, before the tokenizer is needed — rendering **both** the spinner and any failure into the container it is handed -- `warning_slot` on the Text tab, **`doc_status_slot`** on the Document tab -- and returning `None`. The spinner has to go in the slot: inside a translate handler the script cursor is below the panels and the controls row, so a bare `st.spinner` put the only sign of activity below the fold while the error appeared at the top. `@st.cache_resource` is process-global (shared across every session and user, not per-session), so the load happens once per server process, and it does **not** memoize exceptions — a failed load leaves the button live and a later click retries. Loading eagerly at page load put the whole UI behind ~3.6 GB of weights: no tabs, no language pickers, nothing to type into while it read. Consequently the translate buttons are **not** gated on a `model_loaded` flag — there is no cheap way to know the model loads without loading it, so a broken install surfaces on click, next to the action that caused it
- Both tab bodies still execute on every rerun. `st.tabs(..., on_change="rerun")` + `.open` would make them lazy; considered and skipped. The heavy work is already behind button guards, so what it saves is a per-rerun re-encode of the Document tab's output — **not** a doubled payload, as an earlier version of this bullet claimed. `download_button` does **not** ship its `data`: the `DownloadButton` proto has no `data` field at all, and `marshall_file` registers the bytes with the media-file manager and sets only `url`, so the browser receives a link. The real cost is server-side: a UTF-8 encode plus hash of the whole output for the button, and an unchanged `st.code` sent as a ref-hash. Measured on whole-app reruns with populated state — 16.7 ms empty, 17.9 ms at 180 KB, 20.0 ms at 1 MB, so roughly 3 ms per MB across both elements. Against that, `on_change="rerun"` costs a server round-trip per tab switch and risks Streamlit purging the unrendered tab's widget state, which the `setdefault` block above the tabs would silently re-seed to English/French. If revisited, gate only the output rendering, not the whole tab body

- LiteParse ships **no chunker**, so `chunk_text` is where a document becomes translatable pieces: it splits on blank lines, packs blocks greedily under the budget, splits over-budget blocks on sentence boundaries (Latin *and* CJK enders) and finally on hard token windows, and prepends the enclosing markdown heading trail — context that matters because each chunk is translated as an independent prompt
- `chunk_text` accounting has three traps, all covered by tests: the tokenizer prepends a BOS to **every** `encode` call (so `count_tokens` subtracts `token_overhead`, or an N-block chunk is charged N BOS tokens), joining blocks costs a `\n\n` separator each, and BPE still merges across block boundaries — so `flush()` measures the assembled chunk. Drift measures ~1 token per block, far inside the `MAX_CHUNK_TOKENS`/`MAX_INPUT_TOKENS` headroom. `SpecialTokenTokenizer` in the tests simulates the BOS and separator costs; the plain `FakeTokenizer` cannot catch this class of bug, and `DriftingTokenizer` (which spends an extra token per block join) is the only one that reproduces the overflow itself
- When the measured chunk *is* over, `flush()` calls `repack_blocks`, which re-packs whole blocks against measured sizes. It must not call `split_oversized` on the assembled body: that splits at every sentence and dissolves the `\n\n` between blocks, so a 7,330-token document at `MAX_CHUNK_TOKENS` came out as **277 single-sentence chunks instead of 3** — one translation call each, every one stripped of its neighbours. Drift overflow fires on essentially every *full* chunk, so this was the common path, not an edge case. `test_chunk_text_does_not_shatter_a_full_chunk_when_the_estimate_drifts` asserts the chunk **count**; the budget tests only bound chunk size, and hundreds of tiny chunks satisfy an upper bound perfectly
- `pack_by_estimate` is the shared greedy grouper: one token count per unit, plus a `join_cost` charged per join, and the caller measures each finished group once. Measuring every growing candidate instead is **quadratic** — a single 16.8k-token block took 3.85 s and a CJK one 36 s, against 0.16 s / 0.49 s now. `join_cost` is not optional for block callers: omitting the `\n\n` separator let 985 blocks estimated at 5,792 tokens measure 7,760, and that overflow fell through to the fallback that strips heading context
- `repack_blocks` takes the **full trail**, not the caller's deduplicated context, and re-derives context per piece via `leading_headings`. Two ways a piece ends up unlabelled if this is skipped: a piece cut from the middle contains none of the headings the first piece opened with, and the *first* chunk of a document opens before any heading has reached `trail`, so its headings exist only as its own blocks. Its fallback path assembles each sub-group with context too — falling straight through to `split_oversized` is what dropped the labels
- `leading_headings` returns only the headings a chunk **opens** with. De-duplicating context against *every* block in the chunk looks tidier but is wrong: when the next section repeats a heading text inside the same chunk, it strips that heading from the body that actually belongs to it — 102 paragraphs reaching the model labelled only with the document title
- `split_oversized` re-packs sentence units up to the budget rather than emitting one piece per sentence, and strips the BOS prefix before slicing token windows, or `decode` would write the special token back into the translated text
- `hard_windows` pulls a window boundary back (up to `_MAX_CHAR_TOKENS`, four bytes of UTF-8) until the window decodes without U+FFFD. A byte-fallback tokenizer spends several tokens on one character in Thai, Lao, Khmer, Burmese, Amharic and rarer CJK — all in `LANGUAGES` — so a fixed stride cut characters in half, and the halves decoded to U+FFFD with the character **lost outright** before reaching the model. `ByteFallbackTokenizer` in the tests is the only fixture that can see this: it encodes non-ASCII to real UTF-8 bytes and decodes with `errors="replace"`, where the whitespace fakes round-trip perfectly and cannot
- `sentence_units` splits on `(?<=[.!?])\s+|(?<=[。！？])\s*` — the two branches need different whitespace rules. Latin prose puts a space after the ender, and *requiring* one is what keeps `3.14` intact; CJK writes 。 flush against the next sentence, so demanding whitespace there meant real CJK never split at all and fell through to mid-clause hard token windows. Units carry their own trailing gap so concatenating them reproduces the source exactly — rejoining on a space would insert one CJK never had
- When the heading trail would leave less than a quarter of `max_tokens` to work with, `chunk_text` **drops the context** instead of clamping the budget to 1. Clamping shredded the document: a 7,002-token trail against the 7,000 budget turned 13,121 tokens of markdown into 12,082 chunks over 292 s, then 12k `stream_translate` calls. Now 4 chunks in 0.12 s. A chunk carrying less context still translates; a chunk of one token does not. `chunk_text` and `hard_windows` both clamp `max_tokens` to at least 1 — a zero budget made `hard_windows`' boundary pull-back loop spin forever, since a zero-width window never advances past its own start
- Blocks inside a ```` ``` ```` fence never update the heading trail. `_BLANK_LINE_RE` splits a fence at its internal blank line, so a `# clean up the build tree` comment inside one arrived as its own block, read as an H1, and evicted the real heading — every chunk below it was then labelled with a line of shell. The fence flag is toggled by the parity of the marker count per block, so it has to be carried across blocks and cleared again on close
- The heading trail is snapshotted when a chunk *opens* (`pending`), not read at flush time — `trail` advances as blocks are consumed, so flushing against it labels a chunk with the heading of the section that comes *after* it. `trail` stores `heading_line(block)`, **not** the block: blocks split on blank lines, so a heading followed immediately by its opening body line is one block, and storing it whole prepended that body text to every later chunk and charged its tokens against the budget the trail reserves
- `DOCUMENT_TYPES` is PDF + images: liteparse statically links both PDFium and Tesseract into its native module, so neither needs a binary on `PATH` (Tesseract's *training data* is still fetched on first OCR — see above). The tiers below were **probed against liteparse 2.11.1 with real generated files**, not read off its README, whose "Supported Formats" section stops at "Images (`.png`, `.jpg`, `.tiff`, etc.)" and "And more!":
  - **Native, nothing on `PATH`** — PDF, PNG, JPEG, TIFF, WebP, and also **BMP and GIF**. Those last two are genuinely supported and deliberately *not* offered; nobody translates a GIF
  - **Needs LibreOffice on `PATH`** — `.docx`, `.pptx`, `.xlsx`, `.odt`, `.ods`, `.odp`, `.rtf`. They fail with `conversion error: LibreOffice is not installed`, a *conversion* error rather than an unsupported one, because every non-PDF input is converted to PDF before parsing
  - **Rejected outright** (`unsupported file format`) — `.html`, `.epub`, `.heic`/`.heif`, `.ico`, `.tga`, `.jp2`, `.ppm`/`.pgm`, and the entire plain-text family: `.txt`, `.md`, `.csv`, `.json`. **Plain text being unreadable is not a bug**: everything normalizes to PDF first and no code path simply returns bytes as text, so `.txt` has nothing to convert *from*. The `Cannot screenshot text-based format (.<ext>). Convert to PDF first.` string in the native module is the same rule surfacing elsewhere
- liteparse **sniffs content, never the extension** — `parse(bytes)` is handed no filename, so its errors report what the magic bytes said: a `.ppm` comes back as `.pgm`, a `.tga` as `.cur`, and `.md`/`.csv`/`.json` all as `.txt`. `load_document_markdown`'s own `%PDF` sniff is therefore the same question asked the same way, not a workaround

A real fix would be pre-conversion (`sips` ships on every Mac), not a list edit. `test_document_types_are_liteparse_native` pins both halves: both TIFF spellings present, and `heic` absent alongside `docx`/`pptx`/`xlsx`/`html`

- The `cached_document_chunks` tests reference `streamlit_app.cached_document_chunks` with **no** `# ty: ignore` — the editor's incremental LSP flags it `unresolved-attribute` (the `@st.cache_data` decorator trips it), but the `ty check` CLI (the gate) resolves it fine, so adding an ignore would make the CLI fail with `unused-ignore-comment`. Trust the CLI, not the editor squiggle
